# Wiki 질의·대화 기능 확인

2026-09-26, 생성된 Wiki를 읽어 답하는 API·MCP 경로와 대화 이력을 이용한 후속 질문 처리를 구현했다. **기존 검색 대비 평가가 아니라, 고정된 네 사례를 실제 모델로 각 1회 실행한 기능 확인**이다.

## 구현 범위

- `/answer`·MCP `ask_wiki`에 `method="wiki"`, 선택적인 `history`, `max_input_tokens`를 추가했다. 기존 `vector`·`hybrid`·`keyword`와 `/search`는 유지했다.
- 이력이 있으면 질문의 대상을 먼저 해석한다. 모호하면 `clarification_required`로 응답하며 Wiki·DB를 읽지 않는다. 이력이 없는 기존 RAG 요청은 추가 모델 호출 없이 이전 경로로 실행한다.
- Wiki는 전체 목차 → 주제 목차 최대 2개 → 본문 최대 3개를 읽는다. 처음 선택한 본문에서 한 단계의 관련 링크만 추가 탐색한다.
- 답변 모델은 해석된 질문과 Wiki의 출처가 붙은 문단을 읽는다. 과거 답변은 사실 근거로 전달하지 않는다. 답변에서 선택한 근거 ID를 검증한 뒤 코드가 `[1]` 번호와 Wiki·원본 위치를 연결한다.
- Wiki와 인용 원본의 해시, 파일 경로·행 범위를 확인한다. 원본 읽기는 출처 검증용이며 원본 본문을 추가 검색해 답변 모델에 보내지 않는다.

## 실행 조건

모델은 `gemini-3.5-flash-lite`, temperature는 0이다. Wiki 생성 결과는 `431cd15`에 포함된 고정 원본 기반 결과를 사용했다. API는 FastAPI TestClient로 실제 서비스 함수를 호출했다. 따라서 API 프로세스 간 네트워크나 MCP 전송 시간은 포함하지 않는다.

질문은 [cases JSON](wiki-conversation-cases.json)에 실행 전에 기록했다. 후속 질문의 `history`에는 첫 질문과 **이번 실행의 실제 답변**을 전달했다. 모델·질문 파일·코드 해시·Wiki fingerprint와 응답·출처·탐색·사용량은 [results JSON](wiki-conversation-results.json)에 있다.

```bash
uv run python scripts/check_wiki_conversation.py --model gemini-3.5-flash-lite
```

이 명령은 API를 호출하며 비용이 발생한다. API 키는 로컬 `.env`에서 읽고 결과에는 저장하지 않는다.

## 관찰 결과

| 사례 | 답변·동작 | 판정 |
| --- | --- | --- |
| 현재 배포 금지 시간 + 목요일 금지 이유 | 목요일 오후·공휴일 전날·12/22~1/2와 정산 배치·배포 충돌을 답함 | 기대 내용 확인 |
| “그럼 바뀌기 전에는 언제였어?” | 배포 금지 시간으로 해석하고 금요일 오후·공휴일 전날을 답함 | 기대 내용 확인 |
| 배포 시간·승인자 두 변경 대상이 있는 대화 | 어느 항목인지 되물음. `sources=[]`, `trace.reads=[]` | 기대 분기 확인 |
| 원본에 없는 식대 지원 한도 | `insufficient_evidence`, 금액을 생성하지 않음 | 기대 분기 확인 |

첫 질문은 v30·v22·장애 #18을 읽었다. 현재 금지 시간은 v30의 원본 17행, 변경 이유는 v22와 장애 #18의 원인 구절로 확인했다. 후속 질문은 배포 목차와 v5·v16·v22를 읽고, v22 Wiki의 배포 금지 시간 이력을 인용했다. 변경 전 값은 원본 v21의 17행으로 확인했다. 모든 반환 출처가 읽은 페이지에 속하고 원본 행 범위·내용이 유효했다.

후속 질문의 해석은 “현재 배포 금지 시간이 바뀌기 전에는 언제였어?”였다. 이번에는 기대 답을 얻었으나, 어느 변경 시점인지 더 정확히 특정하는 해석과 불필요한 과거 버전 선택을 줄이는 동작은 추가 평가 대상이다.

| 사례 | API 내부 응답 시간 | 생성 호출 | 입력 텍스트 토큰 합계 | 공급자 보고 총 토큰 |
| --- | --- | --- | --- | --- |
| 첫 질문 | 7.83초 | 4 | 10,403 | 10,633 |
| 후속 질문 | 7.03초 | 4 | 5,933 | 6,101 |
| 모호한 대상 | 4.07초 | 1 | 364 | 409 |
| 근거 없음 | 2.17초 | 1 | 319 | 324 |

각 생성 호출 전 `count_tokens` 요청을 별도로 수행한다. 위 생성 호출 수에는 토큰 계산 요청이 포함되지 않고, 전체 응답 시간에는 포함된다. 입력은 재전달된 목차·페이지 내용을 포함하며, 재시도 때도 누적한다. 기본 누적 입력 텍스트 한도는 48,000토큰이다. 공급자의 부가 토큰·출력은 응답 usage에 별도 기록된다.

## 자동 검증과 한계

- DB 연동 포함 테스트 **178개 통과**, 건너뜀 없음. Ruff 통과.
- 해석한 질문이 기존 세 검색 방식에 전달되는지, 모호할 때 검색을 건너뛰는지, 요청 간 대화가 남지 않는지 확인했다.
- 본문 수·링크 1단계 제한, 허용되지 않은 경로·근거 ID 거절, 변경된 Wiki·원본 거절, 입력 한도 초과와 근거 부족 응답을 확인했다.
- API·클라이언트·MCP에서 이력·Wiki 선택·입력 한도 전달을 확인했다. Docker 이미지에도 Wiki와 원본을 포함하고 기본 경로를 명시했다. 실행 중인 서버 배포를 의미하지 않는다.
- LLM의 질문 해석·모호성 판단·주장과 근거의 의미적 일치까지 자동 검증하는 기능은 아니다. 원본 인용이 있는 Wiki 문단을 반환한다는 사실만으로 모든 주장의 정확성을 보장하지 않는다.
- 현재 trace의 모델 사용량은 **질문 해석과 Wiki 경로**다. 기존 RAG 검색·답변은 별도 계측·토큰 한도 연결이 필요하다. 이번 수치로 RAG와 전체 비용·시간을 비교하지 않는다.
- 기존 20문항 전체 및 반복 성능 측정, 모델·입력 예산을 맞춘 A/B/C 비교는 아직 수행하지 않았다.
