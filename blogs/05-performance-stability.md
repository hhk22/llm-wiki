# LLM Wiki v5 — 성능과 안정성의 현재 한계와 개선 방향

> **갱신 중 조회와 작업 처리, 문서 증가에 어떻게 대응할 것인가?**

v4까지 원본 변경을 감지하고 관련 Wiki를 갱신하는 기능을 구현했다. 다음으로 살펴볼 것은 **갱신 중 조회, 오래 걸리는 작업 처리, 문서 증가에 따른 확장 방법**이다.

이 글은 현재 구현을 바탕으로 한 설계 검토다. Worker나 무중단 전환을 새로 구현한 결과가 아니라, 남은 문제와 개선 조건을 정리한다.

## 1. 갱신 중 사용자가 Wiki를 읽으면 어떻게 될까?

현재는 갱신 중 질의를 멈추는 운영을 전제로 한다. 조회 도중 Wiki를 교체하면 목차와 본문의 버전이 달라질 수 있고, 원본이 수정되면 이전 Wiki의 출처 검증도 실패할 수 있다.

개선 방향은 **Wiki와 원본을 함께 보관하고, 한 대화가 같은 구축 버전을 읽도록 하는 것**이다. 아래는 아직 구현하지 않은 설계다.

**① Wiki와 원본을 한 묶음으로 저장한다.**

```text
releases/
├─ build-001/ ── wiki/ + sources/
└─ build-002/ ── wiki/ + sources/

current ---> build-001
```

`build-001`은 개별 문서의 v30 같은 버전이 아니라 Wiki 전체의 구축 버전이다. 공개한 묶음은 수정하지 않고, 출처도 그 안의 원본을 참조한다.

**② 새 묶음을 검증한 뒤 최신 버전 표시만 바꾼다.**

```text
변경된 원본 사본 준비 ---> build-002 갱신 ---> 검증
                                            ├─ 성공: current를 build-002로 전환
                                            └─ 실패: build-001 유지
```

v4의 변경 감지·재사용 방식으로 새 묶음을 만들고, 진행 중인 요청은 처음 선택한 버전의 목차·본문·출처를 끝까지 읽는다.

**③ 후속 질문에도 같은 `build_id`를 전달한다.**

요청마다 최신 버전을 선택하면 후속 질문의 근거가 바뀔 수 있다. 첫 응답에 `build_id`를 반환하고, 클라이언트가 대화 이력과 함께 다시 보내도록 한다.

```text
첫 질문   ---> build-001 선택 ---> 답변 + build_id 반환
              갱신 완료: current를 build-002로 전환
후속 질문 ---> build-001 ID 전달 ---> build-001로 계속 답변
새 대화   ---> ID 없이 시작      ---> 최신 build-002로 답변
```

사용자가 버전을 직접 고를 필요는 없다. 답변에 기준 버전을 표시하고, 최신 변경은 새 대화부터 반영한다. 이전 버전은 사용 중인 동안 보관하며, 만료됐다면 새 대화를 시작하도록 안내한다.

| 검증할 상황 | 기대 결과 |
| --- | --- |
| 목차를 읽은 직후 새 버전으로 전환 | 본문·출처도 처음 선택한 버전에서 읽음 |
| 갱신 후 같은 대화에서 후속 질문 | 기존 `build_id` 유지 |
| 갱신 후 새 대화 시작 | 최신 구축 버전 선택 |

## 2. 오래 걸리는 갱신에는 Worker가 필요한가?

현재는 `update_wiki.py`를 실행하고 터미널에서 완료를 기다린다. 웹에서 갱신을 요청하려면 **요청은 바로 접수하고, 실제 갱신은 Worker가 백그라운드에서 실행하는 구조**로 확장할 수 있다. 아래는 아직 구현하지 않은 설계다.

**① 갱신 요청에 작업 ID를 반환한다.**

```text
현재: CLI 실행 ---> 갱신 처리 ---> 완료까지 기다림

개선안
사용자 ---> API에 갱신 요청 ---> 작업 등록 ---> 작업 ID 반환
                                  │
                                  v
                               Worker
                                  │
                     기존 갱신 로직 실행·검증
                                  │
                         상태·결과 기록 갱신
```

API는 접수한 작업 ID를 바로 반환한다. Worker는 등록된 작업을 가져와 기존 갱신 로직을 실행하고, 진행 상태와 결과를 저장한다.

**② 클라이언트가 작업 ID로 상태를 주기적으로 조회한다.**

예를 들어 10초마다 조회하는 폴링 방식으로 시작할 수 있다. 조회 간격은 설정값이며, 상태 조회는 저장된 기록만 읽는다.

```text
갱신 요청 ---> job-123 받음
                  │
             10초 후 조회 ---> 실행 중
                  │
             10초 후 조회 ---> 실행 중
                  │
             10초 후 조회 ---> 완료 + 결과 ---> 폴링 종료
```

| 작업 상태 | 화면에 표시할 내용 |
| --- | --- |
| 대기 중 | 갱신 요청이 접수됨 |
| 실행 중 | 생성·검증 등 현재 처리 단계 |
| 완료 | 갱신 결과·검증 요약 |
| 실패 | 실패 이유·확인할 기록 |

완료 또는 실패하면 폴링을 멈춘다. 상태를 조회할 때마다 갱신을 다시 실행하는 것은 아니다.

**달라지는 것은 갱신 요청과 결과 확인 방식이다.** 요청한 쪽은 완료까지 연결을 유지할 필요가 없지만, Worker 자체가 LLM 처리 시간을 줄이지는 않는다. 갱신 중에도 같은 버전으로 답변하는 문제는 앞의 버전 관리 설계로 다룬다.

## 3. 문서가 많아지면 필요한 페이지를 어떻게 찾을까?

현재는 **전체 목차 → 주제 목차 → 관련 페이지** 순서로 Wiki를 탐색한다. 문서가 늘면 주제별 `index.md`도 커져, 질문마다 목차를 읽고 페이지를 선택하는 시간과 입력 토큰이 증가할 수 있다.

개선 방향은 **목차를 작게 나누고, 규모가 더 커지면 검색으로 관련 페이지에 바로 접근하는 것**이다. 아래는 아직 구현하지 않은 설계다.

**① 목차를 계층화해 필요한 분류만 읽는다.**

배포 문서가 수천 개라면 하나의 배포 목차에 모두 나열하지 않고, 세부 목차로 나눈다. 다음은 분류 구조의 예시다.

```text
전체 목차
├─ 배포
│  ├─ 현재 정책 ---> 관련 페이지
│  ├─ 변경 이력 ---> 관련 페이지
│  └─ 배포 절차 ---> 관련 페이지
├─ 장애
└─ 온보딩
```

상위 목차에는 바로 아래 분류의 설명과 링크만 담고, 마지막 단계의 목차에 페이지 목록·요약을 둔다. 각 목차의 입력 크기에 상한을 두고, 선택한 분류만 읽도록 한다.

```text
“현재 배포 금지 시간은?”
    ↓
전체 목차 ---> 배포 목차 ---> 현재 정책 목차 ---> 관련 페이지
```

목차 파일만 나누는 것으로 끝나지는 않는다. 조회 코드도 세부 목차를 탐색하도록 바꾸고, 탐색 깊이와 누적 입력량을 제한해야 한다.

**② Wiki 검색으로 후보를 찾고 본문을 읽는다.**

목차가 너무 깊어지면 단계별 LLM 호출이 늘어난다. 이때는 생성된 Wiki의 제목·요약·본문에 검색 인덱스를 두어 관련 페이지 후보를 먼저 찾는다.

```text
질문 ---> Wiki 검색 ---> 관련 페이지 후보
                              ↓
                    본문·관련 링크 확인
                              ↓
                    원본 출처를 검증한 답변
```

기존 검색 기능을 Wiki 페이지에도 적용하는 확장이다. 키워드 검색으로 시작하고, 표현이 다른 질문에서 근거를 놓치는 경우 벡터·하이브리드 검색을 비교한다. 검색 인덱스도 `build_id`별로 구분해 선택한 구축 버전의 페이지만 반환하도록 한다.

| 질문 예시 | 탐색 방식 |
| --- | --- |
| “E-015 해결 방법은?” | 검색으로 해당 페이지에 바로 접근 |
| “배포 절차를 전체적으로 설명해줘” | 목차에서 관련 페이지를 묶어 탐색 |

Wiki에 정리된 설명·변경 이력·출처는 유지하고, **질문에 필요한 근거를 찾아가는 경로를 개선**한다. 문서 수를 늘려가며 답변까지 걸리는 시간·입력 토큰과 필요한 근거의 누락 여부를 함께 확인한다.
