# LLM Wiki v3 — 원본 문서를 종합해 Wiki로 만들기

> **1단계: Wiki 구축 → 2단계: 시점·이력·상충 보강 → 3단계: Wiki 답변·후속 질문**

원본 120개를 읽어 **본문 120개와 목차 5개를 생성**했다. 이후 시점·변경 이력·상충 표시를 보강하고, 생성한 Wiki를 읽어 답하는 경로와 대화 기반 후속 질문 처리를 연결했다.


## 왜 LLM Wiki로 전환하려는가?

### v2의 문제점

> “배포 금지 시간이 금요일 오후에서 목요일 오후로 바뀐 이유가 뭐야?”

v2는 이 질문에 답하기 위해 **가이드 검색 → ‘이유’ 항목의 장애 참조 확인 → 장애 문서 조회 → 답변 생성**을 수행한다. 가이드 v22에서 변경 내용을 찾고, 장애 #18에서 주간 정산 배치와 배포가 겹쳐 정산이 실패한 사건을 읽는다.

답변을 만들 수는 있지만, **두 문서를 종합한 설명은 저장되지 않는다.** 비슷한 질문이 들어오면 다시 검색하고 내용을 연결해야 한다.

### LLM Wiki 전환으로 기대하는 점

**규칙·변경 이유·출처를 Wiki에 미리 정리하고, 여러 질문에서 재사용한다.**

| 기대 효과 | Wiki에서 바꾸는 점 |
| --- | --- |
| 반복되는 종합 부담 감소 | 가이드의 변경 내용과 원인 장애를 함께 설명해 저장 |
| 현재·과거 혼동 감소 | 최신 규칙과 버전별 이력을 구분하고 서로 연결 |
| 필요한 근거의 누락 감소 | 목차·관련 링크로 이유와 이전 규칙을 찾아갈 경로 제공 |

답변 품질과 시간·비용이 기존 검색보다 개선되는지는 비교 평가로 확인해야 한다. 후속 질문의 대상 해석은 Wiki와 기존 검색에 공통으로 적용했다.

## 1단계 — 원본을 종합해 읽을 수 있는 Wiki를 구축했다

`sources/`의 가상 문서 120개를 보존하고, **LLM이 종합한 내용을 `wiki/`에 저장**한다. 배포 버전·장애 사건·오류 코드·FAQ별로 페이지를 나눠 목차에서 필요한 문서를 고를 수 있게 했다.

| 경로 | 역할 |
| --- | --- |
| `wiki/index.md` | 배포·장애·오류·FAQ 주제로 이동하는 전체 목차 |
| `wiki/<주제>/index.md` | 주제 안의 페이지 안내. 배포 목차에는 최신 버전 표시 |
| `wiki/deployments/v22.md` | 배포 가이드 v22의 규칙·변경 이유와 관련 장애 설명 |
| `wiki/incidents/18.md` | 장애 #18의 원인·조치와 관련 정책 |
| `wiki/errors/E-009.md` | 오류 코드의 증상·원인·대응 |
| `wiki/onboarding/Q02.md` | FAQ 답변과 상세 규칙으로 이동하는 링크 |

### 페이지 작성 → 링크 연결 → 목차 생성 → 파일 저장

초기 [`WikiBuilder.build()`](https://github.com/hhk22/llm-wiki/blob/0033be049e056349225b3b02d9f0f8a374504398/src/llm_wiki/wiki_build.py)는 다음 순서로 Wiki를 만들었다.

| 순서 | 처리 | 결과 |
| --- | --- | --- |
| 1. 원본 선택 | 코드가 대상 문서와 명시적 참조로 연결된 원본을 모음 | LLM이 함께 읽을 본문·ID·메타데이터 |
| 2. 내용 작성 | LLM이 원본을 종합하고, 코드는 응답 형식·인용·필수 근거를 검증 | 페이지별 요약·본문·원본 인용 |
| 3. 관계 연결 | 전체 페이지의 요약·출처 목록을 보고 LLM이 관련 페이지 선택 | 관련 Wiki ID와 연결 이유 |
| 4. 목차 생성 | LLM이 주제별 페이지를 묶고, 주제 안내를 모아 전체 목차 작성 | 주제 목차 4개와 전체 목차 1개 |
| 5. Markdown 저장 | 코드가 정해진 형식으로 렌더링하고 실제 경로·출처 행 번호 부착 | 본문 120개와 목차 5개 |

예를 들어 배포 v22 페이지에는 **가이드의 금요일→목요일 변경과 장애 #18의 정산 실패를 함께 설명**하고, 원본 행 번호와 장애 Wiki 링크를 붙였다. 이 단계에서 원본을 종합한 설명을 파일로 보관하고 목차·링크로 찾아갈 수 있게 됐다.

LLM에는 구조화된 응답 형식을 지정한다. 인용이 원문과 다르거나 필수 근거가 빠지면 오류를 전달해 재시도한다. 완료된 작업은 저장해 재개 시 다시 검증하고 재사용한다.

생성 입력에는 평가 질문·정답을 넣지 않는다. 원본·코드 해시, 모델, 프롬프트, 응답, 토큰 사용량은 `wiki/_build/`에 보관한다.

## 2단계 — 생성된 Wiki에 시점·변경 이력·상충 검토를 추가했다

초기 Wiki를 읽어보니, 과거 v22 페이지에도 `현재 규칙`이라는 제목이 남아 있었다. v22 자체의 변경 이유는 설명했지만, 최신 v30에는 규칙별 변경 이력 링크가 없어 **현재 규칙에서 언제·왜 바뀌었는지 따라가기 어려웠다.**

이를 보완하고, 문서 사이에 설명되지 않는 모순도 표시할 수 있도록 다음 기능을 추가했다.

| 대상 | 1단계 결과 | 2단계에서 추가한 것 |
| --- | --- | --- |
| 과거 페이지의 시점 | v22에도 `현재 규칙` 표현이 남음 | `v22 당시 규칙`으로 표시하고 최신 v30 링크 추가 |
| 최신 페이지의 변경 이력 | 규칙별로 변경 버전을 연결한 이력이 없음 | 변경 전후 값·이유·출처와 변경 버전·원인 장애 링크 추가 |
| 문서 간 상충 | 별도의 상충 검토 단계가 없음 | 원본·이력을 LLM이 검토하고 후보가 있으면 `확인 필요` 표시 |

### 변경 이력은 코드로 계산한다 — `history`

**연속 버전의 같은 규칙을 비교해, 값이 바뀐 항목에 근거와 링크를 붙인다.**

```text
원본 가이드 정렬 ---> 연속 버전의 같은 규칙 비교 ---> 값 변경 시 history 기록 ---> Wiki에 표시

history: 전후 원문 · 변경 · 이유 · 명시된 장애 참조
Wiki: 해당 버전까지의 이력 + 변경 문서 · 장애 링크
```

| 비교 | 배포 금지 시간의 변화 | 연결 근거 |
| --- | --- | --- |
| v21 → v22 | 금요일 오후 → **목요일 오후** · 공휴일 전날 유지 | 전후 원문 · v22 변경·이유 · **장애 #18** |
| v24 → v25 | 기존 금지 시간 + **12/22~1/2 연말 동결** | 전후 원문 · v25 변경·이유 |

[최신 v30](../wiki/deployments/v30.md) → **v22·v25·장애 #18 링크** 포함 · [과거 v22](../wiki/deployments/v22.md) → **v22까지의 이력**만 표시

**변경본 반영 — 원본 변경 후 전체 재구축**

```text
원본 추가·수정 ---> Wiki 전체 재구축 ---> 이력·상충 반영 ---> 검증

재구축: 새 출력 폴더에 본문 · 링크 · 목차 생성
반영: history 재계산 + 상충 재검토 + 페이지에 반영
검증: verify_wiki.py로 해시 · 인용 · 링크 · 이력 확인
```

| 원본 변경 예시 | 이력 재계산 | 페이지에 반영되는 결과 |
| --- | --- | --- |
| **v31 추가** | v30 → v31 비교 | 최신 기준·링크를 v31로 갱신. v30 이력은 v30까지 표시 |
| **기존 v22 수정** | v21 → v22, v22 → v23 재비교 | 각 페이지의 버전 범위에 맞춰 수정된 이력 반영 |

> **계산 기준** — 최신 = 구축 원본의 최대 버전(현재 v30). 값이 같거나 공백 서식만 다르면 이력 제외. 빠진 버전·항목의 변경 시점은 추측하지 않는다.
>
> **반영 범위** — 파일 수정만으로 자동 반영되지 않는다. `--resume`은 동일 원본의 중단 작업 재개용. `history`는 버전 간 규칙 차이를 기록하며, 같은 파일의 편집 이력은 보관하지 않는다.

### 상충 후보는 LLM이 검토한다 — `review`

예를 들어 **배포 가이드 v30은 “목요일 오후 배포 금지”, FAQ는 “목요일 오후 배포 허용”**이라고 설명한다고 가정하자. LLM은 버전·변경 이력을 함께 보고, 이 차이가 설명되지 않으면 상충 후보로 남긴다.

Wiki에는 양쪽 주장·출처와 함께 **“FAQ의 적용 시점과 예외 여부 확인 필요”**를 표시한다. 어느 쪽이 맞는지 자동 확정하거나 원본을 수정하지 않는다.

**최종 Wiki 구성 — 위 가상 상충 사례를 포함한 예시**

```text
배포 가이드 v30
│
├─ 기존 설명·규칙·출처       ← 기존 본문
├─ 규칙별 변경 이력         ← history 추가
│   ├─ v22: 금요일 → 목요일 금지
│   └─ v25: 연말 동결 추가
├─ 확인 필요                ← review에 상충 후보가 있을 때 추가
│   ├─ 가이드: 목요일 오후 배포 금지 + 출처
│   ├─ FAQ: 목요일 오후 배포 허용 + 출처
│   └─ FAQ의 적용 시점과 예외 여부 확인 필요
└─ 관련 Wiki 링크           ← 기존 링크
```

상충 후보는 **관련 Wiki 페이지와 최신 배포 가이드에 함께 표시**한다.

## 구축 검증 — 이력 연결과 상충 표시가 동작하는가?

**같은 배포 금지 시간을 설명하는 두 문서가 일치할 때와 모순될 때를 비교했다.** 실제 실험에는 가이드 v21·v22·v24·v25·v30과 FAQ Q02를 함께 넣었고, 아래는 비교할 두 문서의 구절이다.

**① 정상 입력 — 두 문서 모두 목요일 오후 배포 금지**

| 문서 #1 · 배포 가이드 v30 | 문서 #2 · FAQ Q02 |
| --- | --- |
| **현재 규칙**<br>배포 금지 시간: 목요일 오후, 공휴일 전날, 12/22~1/2 연말 동결 | **Q. 배포 금지 시간이 있나요?**<br>목요일 오후, 공휴일 전날, 12월 22일부터 1월 2일까지는 배포하지 않는다. |

**기대:** 같은 금지 시간을 설명하므로 상충 후보가 없어야 한다.<br>
**실제:** 후보 **0건**. 함께 넣은 과거 버전의 정상 변경도 상충으로 잡지 않았다.

**② 상충 입력 — FAQ만 목요일 오후 배포 허용으로 변경**

| 문서 #1 · 배포 가이드 v30 유지 | 문서 #2 · FAQ Q02의 실험용 입력 |
| --- | --- |
| **현재 규칙**<br>배포 금지 시간: 목요일 오후, 공휴일 전날, 12/22~1/2 연말 동결 | **Q. 배포 금지 시간이 있나요?**<br>**현재 목요일 오후에는 배포할 수 있다.** 공휴일 전날과 12월 22일부터 1월 2일까지는 배포하지 않는다. |

**기대:** 목요일 오후의 **금지 ↔ 허용**을 상충 후보로 잡고, 두 문서를 근거로 제시해야 한다.<br>
**실제:** FAQ Q02와 v30의 원문을 근거로 후보 **1건** 반환.

별도 단위 테스트에서는 후보가 Wiki의 **`확인 필요`에 양쪽 출처와 함께 표시되고, 기존 규칙은 덮어쓰지 않는지** 확인했다.

전체 구축에서는 원본 120개에 대응하는 본문 120개·목차 5개, 링크·인용을 검사했다. 변경 이력 14건은 원본에서 다시 계산해 저장된 페이지와 대조했으며, 실제 배포 관련 원본 67개에서는 상충 후보가 나오지 않았다.

실험은 `gemini-3.5-flash-lite`로 조건별 1회 실행했고, 원본 파일은 보존한 채 입력만 바꿨다. 전체 상충의 탐지나 설명의 정확성을 보장하는 평가는 아니다. [실험 입력·응답](../evaluation/wiki-history-conflict-probe.json) · [이력·상충 검증 기록](../evaluation/wiki-history-review.md) · [초기 생성 기록](../evaluation/wiki-build-review.md)

## 3단계 — Wiki를 읽고 대화의 후속 질문에 답한다

`POST /answer`와 MCP `ask_wiki`에 **`method="wiki"`**를 추가했다. 임베딩·벡터 DB 없이 Wiki의 목차와 링크를 따라 근거를 찾고 답한다.

```text
앞선 대화: 현재 배포 금지 시간과 목요일 금지 이유를 질문·답변
    ↓
후속 질문: “그럼 바뀌기 전에는?”
    ↓
대상 해석: “배포 금지 시간이 바뀌기 전에는?”
    ↓
Wiki 탐색: 배포 목차 → v22의 변경 이력 확인
    ↓
답변: “금요일 오후·공휴일 전날” + Wiki·원본 출처
```

호출자가 최근 대화를 함께 전달한다. **이전 답변은 질문의 대상을 해석하는 데만 쓰고, 답변 근거는 Wiki에서 새로 읽는다.** 탐색은 주제 목차 최대 2개·본문 최대 3개로 제한하며, Wiki와 인용 원본이 구축 당시 내용과 일치하는지 확인한다.

| 실제 모델로 확인한 상황 | 결과 |
| --- | --- |
| 현재 배포 금지 시간과 이유 질문 | 금지 시간·정산 실패 이유를 출처와 함께 답함 |
| 이어서 “그럼 바뀌기 전에는?” | 금요일 오후·공휴일 전날을 답함 |
| 변경 대상이 둘인데 “그 전에는?” | 대상을 되묻고 탐색하지 않음 |
| 원본에 없는 식대 지원 한도 질문 | 금액을 만들지 않고 근거 부족 응답 |

**네 사례를 각 1회 확인한 결과**이며, 기존 검색 대비 품질 우위를 측정한 것은 아니다. 테스트·탐색 경로·토큰 사용량 등은 [질의·대화 기능 확인 기록](../evaluation/wiki-conversation-review.md)에 남겼다.

## v4로 이어질 작업 — 원본 변경에 따른 Wiki 갱신

v3는 고정된 원본의 Wiki 구축과 질의 비교까지 진행한다. 원본이 바뀌면 수동으로 전체를 다시 생성하며, **변경 감지·영향받는 Wiki의 부분 갱신·갱신 이력 관리**는 [v4 지식 갱신](04-wiki-updates.md)에서 다룬다.
