# LLM Wiki v3 — 원본 문서를 종합해 Wiki로 만들기

> **1단계: Wiki 구축 → 2단계: 시점·이력·상충 보강 → 3단계: Wiki 답변·후속 질문**

원본 120개를 읽어 **본문 120개와 목차 5개를 생성**했다. 이후 시점·변경 이력·상충 표시를 보강하고, 생성한 Wiki를 읽어 답하는 경로와 대화 기반 후속 질문 처리를 연결했다.

| 단계 | 구현한 내용 | 상태 |
| --- | --- | --- |
| 1. Wiki 구축 | 원본 종합 → 페이지·관련 링크·목차·출처 생성 | 완료 |
| 2. 생성물 보강 | 현재·과거 표시, 규칙별 변경 이력, 상충 후보 표시 | 완료 |
| 3. Wiki 질의·대화 | 목차·페이지 탐색, 출처 답변, 후속 질문 해석·되묻기 | 구현·기능 확인 |
| 다음: 비교 평가 | 기존 검색과 동일 조건에서 품질·시간·비용 비교 | 미측정 |

## 왜 LLM Wiki로 전환하려는가?

### v2의 문제점

> “배포 금지 시간이 금요일 오후에서 목요일 오후로 바뀐 이유가 뭐야?”

v2는 이 질문에 답하기 위해 **가이드 검색 → ‘이유’ 항목의 장애 참조 확인 → 장애 문서 조회 → 답변 생성**을 수행한다. 가이드 v22에서 변경 내용을 찾고, 장애 #18에서 주간 정산 배치와 배포가 겹쳐 정산이 실패한 사건을 읽는다.

답변을 만들 수는 있지만, **두 문서를 종합한 설명은 저장되지 않는다.** 비슷한 질문이 들어오면 다시 검색하고 내용을 연결해야 한다.

### LLM Wiki 전환으로 기대하는 점

**규칙·변경 이유·출처를 Wiki에 미리 정리하고, 여러 질문에서 재사용한다.**

| 기대 효과 | Wiki에서 바꾸는 점 |
| --- | --- |
| 반복되는 종합 부담 감소 | 가이드의 변경 내용과 원인 장애를 함께 설명해 저장 |
| 현재·과거 혼동 감소 | 최신 규칙과 버전별 이력을 구분하고 서로 연결 |
| 필요한 근거의 누락 감소 | 목차·관련 링크로 이유와 이전 규칙을 찾아갈 경로 제공 |

답변 품질과 시간·비용이 기존 검색보다 개선되는지는 비교 평가로 확인해야 한다. 후속 질문의 대상 해석은 Wiki와 기존 검색에 공통으로 적용했다.

## 1단계 — 원본을 종합해 읽을 수 있는 Wiki를 구축했다

`sources/`의 가상 문서 120개를 보존하고, **LLM이 종합한 내용을 `wiki/`에 저장**한다. 배포 버전·장애 사건·오류 코드·FAQ별로 페이지를 나눠 목차에서 필요한 문서를 고를 수 있게 했다.

| 경로 | 역할 |
| --- | --- |
| `wiki/index.md` | 배포·장애·오류·FAQ 주제로 이동하는 전체 목차 |
| `wiki/<주제>/index.md` | 주제 안의 페이지 안내. 배포 목차에는 최신 버전 표시 |
| `wiki/deployments/v22.md` | 배포 가이드 v22의 규칙·변경 이유와 관련 장애 설명 |
| `wiki/incidents/18.md` | 장애 #18의 원인·조치와 관련 정책 |
| `wiki/errors/E-009.md` | 오류 코드의 증상·원인·대응 |
| `wiki/onboarding/Q02.md` | FAQ 답변과 상세 규칙으로 이동하는 링크 |

### 페이지 작성 → 링크 연결 → 목차 생성 → 파일 저장

초기 [`WikiBuilder.build()`](https://github.com/hhk22/llm-wiki/blob/0033be049e056349225b3b02d9f0f8a374504398/src/llm_wiki/wiki_build.py)는 다음 순서로 Wiki를 만들었다.

| 순서 | 처리 | 결과 |
| --- | --- | --- |
| 1. 원본 선택 | 코드가 대상 문서와 명시적 참조로 연결된 원본을 모음 | LLM이 함께 읽을 본문·ID·메타데이터 |
| 2. 내용 작성 | LLM이 원본을 종합하고, 코드는 응답 형식·인용·필수 근거를 검증 | 페이지별 요약·본문·원본 인용 |
| 3. 관계 연결 | 전체 페이지의 요약·출처 목록을 보고 LLM이 관련 페이지 선택 | 관련 Wiki ID와 연결 이유 |
| 4. 목차 생성 | LLM이 주제별 페이지를 묶고, 주제 안내를 모아 전체 목차 작성 | 주제 목차 4개와 전체 목차 1개 |
| 5. Markdown 저장 | 코드가 정해진 형식으로 렌더링하고 실제 경로·출처 행 번호 부착 | 본문 120개와 목차 5개 |

예를 들어 배포 v22 페이지에는 **가이드의 금요일→목요일 변경과 장애 #18의 정산 실패를 함께 설명**하고, 원본 행 번호와 장애 Wiki 링크를 붙였다. 이 단계에서 원본을 종합한 설명을 파일로 보관하고 목차·링크로 찾아갈 수 있게 됐다.

LLM에는 구조화된 응답 형식을 지정한다. 인용이 원문과 다르거나 필수 근거가 빠지면 오류를 전달해 재시도한다. 완료된 작업은 저장해 재개 시 다시 검증하고 재사용한다.

생성 입력에는 평가 질문·정답을 넣지 않는다. 원본·코드 해시, 모델, 프롬프트, 응답, 토큰 사용량은 `wiki/_build/`에 보관한다.

## 2단계 — 생성된 Wiki에 시점·변경 이력·상충 검토를 추가했다

초기 Wiki를 읽어보니, 과거 v22 페이지에도 `현재 규칙`이라는 제목이 남아 있었다. v22 자체의 변경 이유는 설명했지만, 최신 v30에는 규칙별 변경 이력 링크가 없어 **현재 규칙에서 언제·왜 바뀌었는지 따라가기 어려웠다.**

이를 보완하고, 문서 사이에 설명되지 않는 모순도 표시할 수 있도록 다음 기능을 추가했다.

| 대상 | 1단계 결과 | 2단계에서 추가한 것 |
| --- | --- | --- |
| 과거 페이지의 시점 | v22에도 `현재 규칙` 표현이 남음 | `v22 당시 규칙`으로 표시하고 최신 v30 링크 추가 |
| 최신 페이지의 변경 이력 | 규칙별로 변경 버전을 연결한 이력이 없음 | 변경 전후 값·이유·출처와 변경 버전·원인 장애 링크 추가 |
| 문서 간 상충 | 별도의 상충 검토 단계가 없음 | 원본·이력을 LLM이 검토하고 후보가 있으면 `확인 필요` 표시 |

### 변경 이력은 코드로 계산한다 — `history`

원본 배포 가이드를 버전순으로 정렬하고, **연속 버전의 `현재 규칙`에서 같은 항목을 비교**한다. 값이 바뀌면 변경 전후 원문과 해당 버전의 ‘변경’·‘이유’를 `history`에 담는다. 이유에 명시된 장애도 연결한다.

예를 들어 배포 금지 시간은 다음과 같이 연결된다.

| 비교한 원본 | 확인한 변경 | Wiki에 연결할 근거 |
| --- | --- | --- |
| v21 → v22 | 금요일 오후 → 목요일 오후. 공휴일 전날은 유지 | 두 버전의 규칙 원문, v22의 변경·이유, 장애 #18 |
| v24 → v25 | 기존 금지 시간에 12/22~1/2 연말 동결 추가 | 두 버전의 규칙 원문, v25의 변경·이유 |

이 정보를 페이지에 반영해 [최신 v30](../wiki/deployments/v30.md)에서 **v22·v25와 장애 #18로 바로 이동**할 수 있게 했다. [과거 v22](../wiki/deployments/v22.md)에는 v22까지의 이력만 담고, 이후 v25의 변경은 넣지 않는다.

같은 배포 가이드 계열의 최대 버전을 최신으로 삼으며, 현재 원본에서는 v30이다. ‘현재’는 구축에 사용한 원본 기준이다. 공백 서식 차이는 제외하고, 빠진 버전이나 항목의 변경 시점은 추측하지 않는다.

### 상충 후보는 LLM이 검토한다 — `review`

배포 가이드와 본문에서 ‘배포 가이드’를 언급한 원본을 골라, **본문·메타데이터·`history`를 LLM에 함께 전달**한다. 변경 이력으로 설명되는 차이와 추가 확인이 필요한 모순을 구분하기 위해서다.

| 예시 | 처리 |
| --- | --- |
| v21은 금요일 금지, v22는 목요일 금지 | 정상적인 버전 변경이므로 `history`로 설명 |
| 가상 상충 사례: 현재 가이드는 목요일 금지인데 FAQ는 목요일 허용이라고 주장 | 상충 후보로 `review`에 기록하고 양쪽 원문·출처 표시 |

LLM의 응답은 검토한 원본 ID와 상충 후보 목록이다. 인용이 입력 원문에 실제로 있는지, 서로 다른 문서의 근거를 포함하는지 검증한다. 후보가 있으면 **`확인 필요`로 표시**하고, 어느 쪽이 맞는지 자동 결정하지 않는다.

### 두 결과를 페이지에 반영한다

[`render_page()`](../src/llm_wiki/wiki_content.py)에 기존 본문·관련 링크와 함께 `history`, `review`를 전달한다.

| 전달하는 값 | 페이지에 반영하는 내용 |
| --- | --- |
| 기존 `page`·`links` | 종합 설명·출처·관련 Wiki 링크 |
| `history` | 해당 버전까지의 규칙별 변경 이력·이유·근거 링크 |
| `review` | 해당 페이지와 관련된 상충 후보. 최신 배포 가이드에도 함께 표시 |

**기존 생성 작업 33개는 재검증해 재사용했다.** 이력을 코드로 계산하고 상충 검토를 추가한 뒤, 결과를 반영해 Markdown 전체를 다시 저장했다. 코드 변경으로 입력 프롬프트가 달라진 작업은 `--resume --accept-code-change`에서 이전 결과를 보관하고 다시 생성하도록 보완했다.

## 구축 검증 — 이력 연결과 상충 표시가 동작하는가?

생성 모델은 `gemini-3.5-flash-lite`다. 연속 버전의 규칙 항목에서 **변경 14건**을 확인하고, 배포 관련 원본 **67개**를 상충 검토에 사용했다.

| 검토 조건 | 결과 |
| --- | --- |
| 실제 배포 관련 원본 67개 | 상충 후보 0건 |
| 별도 실험: 정상 버전 이력과 FAQ | 후보 0건 |
| 별도 실험: FAQ를 “현재 목요일 오후 배포 허용”으로 변경 | FAQ와 v30 사이 후보 1건 |

별도 실험은 원본 파일을 수정하지 않고 입력만 바꿔 각 1회 실행했다. **후보 0건이 상충 부재를 증명하거나, 이 실험이 전수 탐지 성능을 보장하지는 않는다.**

| 확인 항목 | 최신 결과 |
| --- | --- |
| 생성 파일 | 본문 120개·목차 5개, 누락·중복 없음 |
| 링크 | 2,166개 대상 확인 |
| 생성 본문의 근거 인용 | 978개 원문 일치 |
| 시점·이력 | 원본에서 다시 계산·렌더링해 저장된 페이지와 대조 |
| 구축 단계 코드 검증 | DB 연동 포함 당시 테스트 146개 통과, Ruff 통과 |

인용 일치와 링크 검증만으로 설명의 의미·인과관계·완전성까지 보장하지는 않는다. 호출·토큰·검증 범위는 [초기 생성 기록](../evaluation/wiki-build-review.md)과 [이력·상충 검증 기록](../evaluation/wiki-history-review.md)에 남겼다.

## 3단계 — Wiki를 읽고 대화의 후속 질문에 답한다

**대화 이력 + 질문 → 대상 해석 → 목차·페이지 탐색 → 근거를 다시 확인한 답변**

`POST /answer`와 MCP `ask_wiki`에 **`method="wiki"`**를 추가했다. 기존 `vector`·`hybrid`·`keyword` 검색과 답변은 유지하며, Wiki 경로는 임베딩·벡터 DB 없이 Markdown을 탐색한다.

### “그럼 바뀌기 전에는?”을 어떻게 처리하는가?

호출하는 쪽에서 최근 `user`·`assistant` 대화를 `history`로 함께 전달한다. 서버에 대화를 저장하지 않으므로 요청 간 이력이 섞이지 않는다.

| 순서 | 실제 기능 확인에서의 처리 |
| --- | --- |
| 앞선 대화 | 현재 배포 금지 시간과 목요일 오후 금지 이유를 질문·답변 |
| 후속 질문 | “그럼 바뀌기 전에는 언제였어?” |
| 대상 해석 | “현재 배포 금지 시간이 바뀌기 전에는 언제였어?”로 풀어 씀 |
| 근거 재조회 | 배포 목차와 버전 페이지를 읽고 v22의 변경 이력에서 이전 규칙 확인 |
| 답변 | 금요일 오후·공휴일 전날이었다고 답하고 Wiki 절·원본 행 범위를 연결 |

**이전 답변은 대상 해석의 보조 정보다.** 탐색과 답변 단계에는 해석한 질문과 새로 읽은 Wiki 근거를 전달한다. 이전 답변 자체를 사실 근거로 사용하지 않는다. 이 질문 해석 단계는 기존 검색 기반 답변에도 동일하게 적용한다.

대상이 여러 개면 추측해서 검색하지 않는다. 배포 금지 시간과 승인자 변경을 함께 이야기한 뒤 “그 전에는?”이라고 물으면, **어느 항목인지 되묻는 `clarification_required` 응답**을 반환한다.

### 탐색 범위와 출처를 제한한다

| 항목 | 현재 구현 |
| --- | --- |
| 읽기 범위 | 전체 목차 → 주제 목차 최대 2개 → 본문 최대 3개. 처음 선택한 본문의 관련 링크를 1단계만 탐색 |
| 출처 | 읽은 Wiki 근거에만 답변 번호 부여. Wiki 경로·절과 원본 ID·행 범위·인용문 반환 |
| 원본 일치 | Wiki·인용 원본의 구축 해시를 확인. 원본은 출처 검증에 사용하고 답변 모델에는 Wiki 근거 제공 |
| 대화·입력 한도 | 최근 발화 최대 12개·합계 16,000자. 질문 해석부터 Wiki 답변까지 누적 입력 텍스트 기본 48,000토큰 |
| 관찰 기록 | 해석한 질문, 읽은 파일·탐색 경로·문자 수, 단계별 모델 호출·사용량, 전체 응답 시간 |

한도 초과는 `budget_exceeded`, 근거 부족은 `insufficient_evidence`로 구분한다. 프롬프트 텍스트는 호출 전 토큰을 계산하며 재시도 입력도 합산한다. 공급자의 부가 토큰·출력은 응답 usage에 따로 남긴다.

### 실제 모델로 네 가지 동작을 확인했다

| 고정한 기능 확인 질문 | 단회 실행 결과 |
| --- | --- |
| 현재 배포 금지 시간과 목요일 금지 이유 | 현재 시간·정산 실패 이유를 원본 출처와 함께 답함 |
| 위 답변에 이어 “그럼 바뀌기 전에는?” | 배포 금지 시간으로 해석하고 금요일 오후·공휴일 전날을 답함 |
| 변경 대상이 둘인 대화에서 “그 전에는?” | 대상을 되묻고 Wiki 탐색을 실행하지 않음 |
| 원본에 없는 식대 지원 한도 | 금액을 만들지 않고 근거 부족 응답 |

전체 테스트는 **DB 연동 포함 178개 통과**, Ruff도 통과했다. 질문·답변·출처·호출별 토큰은 [질의·대화 기능 확인 기록](../evaluation/wiki-conversation-review.md)에 남겼다. 네 사례의 단회 동작 확인이며, 기존 검색 대비 품질 우위나 성능 개선을 입증한 결과는 아니다.

## 남은 검증 — 기존 검색과 같은 조건으로 비교한다

기존 20문항·정답은 유지하고, 추가 종합·후속·근거 부족 질문은 별도 세트로 고정해 점수를 분리한다. 같은 원본·질문으로 **답변 내용과 누락, 현재·과거 구분, 원본 출처, 시간·토큰**을 비교한다. 위 기능 확인 사례는 비교 평가와 구분한다.

[v2의 문서 Hit@3 20/20](https://github.com/hhk22/llm-wiki/blob/30b5274/blogs/02-search-quality.md)은 필요한 문서를 확보한 결과다. Wiki 페이지 적중률과 직접 비교하지 않고, **답변이 정확하며 읽은 근거와 원본이 이를 뒷받침하는지**를 공통 기준으로 삼는다.

후속 질문에서는 대화 맥락 처리의 효과와 Wiki의 효과를 구분한다.

| 비교 조건 | 확인할 효과 |
| --- | --- |
| A. 기존 검색·답변 그대로 | 기준선 |
| B. 기존 검색·답변 + 대화 맥락 처리 | A 대비 맥락 처리의 효과 |
| C. Wiki 답변 + 같은 대화 맥락 처리 | B 대비 Wiki의 효과 |

A·B는 `vector`·`hybrid`·`keyword`별로 기록한다. B·C의 대화 이력·질문 해석 방식·답변 모델·입력 토큰 한도를 맞추고, Wiki 생성·페이지 선택 설정도 고정해 남긴다. 원본 검색까지 추가하는 실험은 Wiki만 읽은 결과와 분리한다.

현재 API trace의 모델 사용량은 질문 해석·Wiki 단계만 포함한다. 기존 RAG 검색·답변에도 동일 예산과 사용량 계측을 연결한 뒤 전체 시간·비용을 비교해야 한다.

개선·동일·퇴보를 모두 기록하고 시간은 반복 측정한다. Wiki 사전 생성 비용도 별도로 포함해 전환의 효과를 판단한다.

## v4로 이어질 작업 — 원본 변경에 따른 Wiki 갱신

v3는 고정된 원본의 Wiki 구축과 질의 비교까지 진행한다. 원본이 바뀌면 수동으로 전체를 다시 생성하며, **변경 감지·영향받는 Wiki의 부분 갱신·갱신 이력 관리**는 v4에서 다룬다.
