# LLM Wiki v3 — 원본 문서를 종합해 Wiki로 만들기

> **원본 120개 → 주제별 Wiki 생성 → Wiki를 읽고 답변·후속 질문**

*Wiki 생성과 초기 구축을 완료했다. Wiki 기반 질의·후속 질문은 구현 계획이며, 기존 검색과의 답변 비교는 질의 기능 구현 후 진행한다.*

## 왜 LLM Wiki로 전환하려는가?

### v2의 문제점

> “배포 금지 시간이 금요일 오후에서 목요일 오후로 바뀐 이유가 뭐야?”

이 질문에 필요한 근거는 **가이드 v22**의 변경 내용과 **장애 리포트 #18**의 사건 설명이다. v2는 정책의 변경 이유를 묻는 질문에서 다음과 같이 근거를 보강한다.

**가이드 검색 → 문서의 ‘이유’ 항목에서 장애 참조 확인 → 해당 장애 문서 조회 → 모은 근거로 답변 생성**

가이드 v22가 선택되면 ‘이유’ 항목의 장애 #18 참조를 따라 원문을 조회하고, 주간 정산 배치와 배포가 겹쳐 정산이 실패했다는 내용을 답변 근거에 포함한다. 하지만 **두 문서를 종합한 설명은 재사용할 Wiki로 저장되지 않는다.** 다른 사용자가 비슷한 질문을 하면 다시 검색·참조 조회를 거쳐 내용을 종합해 답변한다.

사전 종합이 답변 품질과 처리 비용에 어떤 차이를 만드는지는 Wiki 구현 후 비교한다.

### LLM Wiki 전환으로 기대하는 점

**LLM이 원본들을 주제별 Wiki로 미리 종합하고, 그 결과를 여러 질문에서 재사용한다.**

- **종합 결과 재사용:** 규칙·변경 이유·원본 출처를 함께 정리해, 질문마다 관계를 다시 구성하는 부담을 줄인다.
- **현재·과거 혼동 감소:** 현재 규칙과 변경 이력을 구분해 저장하고, 질문에 맞는 내용을 읽어 답한다.
- **근거 누락 감소:** 관련 절·링크로 근거를 연결해, 종합 답변과 “왜?”, “변경 전에는?” 같은 후속 질문에 활용한다.

## 구현 1 — LLM이 Wiki를 생성한다

기존 `sources/`의 가상 문서 120개를 사용한다. 원본은 보존하고, **LLM이 종합한 Markdown을 `wiki/`에 저장**한다.

1. **단위별 작성** — 대상 원본과 참조로 연결된 원본을 함께 읽고 배포 버전·장애 사건·오류 코드·FAQ별 페이지를 생성한다.
2. **관계 연결** — 페이지 요약과 출처를 바탕으로 관련 링크를 연결한다.
3. **목차 생성** — 페이지 요약을 주제별로 묶어 탐색의 시작점으로 삼는다.

**배포 이력이나 장애 전체를 한 파일에 담으면, 질문과 무관한 내용까지 읽는 범위가 커질 수 있다.** 배포는 버전별, 장애는 사건별로 나누고 목차에서 필요한 페이지만 선택한다.

| 페이지 | 담을 내용 |
| --- | --- |
| `wiki/index.md` | 주제별 짧은 설명과 각 주제 목차 링크 |
| `wiki/deployments/index.md` | 최신 버전 표시, 버전별 변경 요약과 링크 |
| `wiki/deployments/v30.md` | v30 시점의 배포 규칙과 원본 출처 |
| `wiki/deployments/v22.md` | v22 시점의 규칙, 변경 전후 차이·이유·원본 출처·관련 장애 링크 |
| `wiki/incidents/index.md` | 장애별 증상·원인의 짧은 요약과 링크 |
| `wiki/incidents/18.md` | 장애 #18의 원인·조치와 배포 정책에 반영된 내용 |
| `wiki/errors/E-009.md` | 오류 E-009의 증상·대응과 관련 장애 링크 |
| `wiki/onboarding/Q02.md` | 배포 금지 시간 FAQ와 상세 규칙 링크 |

다른 버전·사건·오류·FAQ도 같은 단위로 생성하며, 오류·FAQ 폴더에도 `index.md`를 둔다. 장애 #18은 버전 번호가 아니므로 `v18.md` 대신 `18.md`로 구분한다.

질의 단계에서는 **“목요일 오후 금지로 바뀐 이유”**를 물으면 배포 목차에서 `v22.md`를 선택하고, 사건의 상세 내용이 필요할 때 `incidents/18.md`를 읽도록 구현할 예정이다.

파일을 나누더라도 **각 페이지에 관련 원본을 종합한 설명을 담는다.** 원본을 복사하고 링크만 붙이는 것으로 끝내지 않는다.

오류 코드·장애 번호는 원본 식별자를 유지한다. 생성 입력에서 평가 질문·정답을 제외하고, 재현을 위해 원본 해시·모델·프롬프트·생성 시점과 결과물을 보관한다.

### 생성 결과

`gemini-3.5-flash-lite`로 **본문 120개와 목차 5개를 생성했다.** [배포 v22 Wiki](../wiki/deployments/v22.md)에는 가이드의 금요일→목요일 변경과 장애 #18의 정산 실패를 종합한 설명, 원본 행 단위 출처, 장애 Wiki 링크가 담겼다.

| 확인 항목 | 결과 |
| --- | --- |
| 파일·목차 | 본문 120개, 목차 5개 — 누락·중복 없음 |
| 링크·출처 | 링크 1,175개 대상 확인, 근거 인용 978개 원문 일치 |
| 코드 검증 | 기존 검색·DB 연동을 포함한 테스트 135개 통과 |

원문 인용이 다르거나 근거가 빠진 결과는 다시 생성했다. 완료된 호출은 저장해 중단 후 재사용하고, 재시도에는 앞서 발견한 오류도 함께 전달한다.

**이 검증이 모든 설명의 정확성을 보장하지는 않는다.** 예를 들어 v30은 현재 규칙을 담았지만 규칙별 변경 이력으로 직접 연결되는 링크는 아직 없다. 종합 내용·시점·링크의 충분성은 다음 단계에서 검토한다. 호출·토큰과 검증 범위는 [생성 기록](../evaluation/wiki-build-review.md)에 남겼다.

## 구현 2 — 현재 규칙과 변경 이력을 구분한다

**과거 규칙이 현재 규칙으로 섞이지 않도록** 각 버전 페이지에 적용 시점을 명시하고, 배포 목차에서 최신 버전을 가리킨다.

버전 표시와 최신 페이지 연결은 생성기에 반영했다. 규칙별 변경 이력 연결과 상충 내용의 처리는 다음 검토 대상이다.

같은 배포 가이드 계열에서는 숫자 버전이 가장 큰 원본을 현재 기준으로 삼는다. 고정 원본에서는 `deployments/index.md`가 `v30.md`를 최신으로 표시하며, `v22.md`의 규칙은 v22 시점의 이력으로 읽는다. 다른 종류의 문서까지 버전 숫자로 우선순위를 정하지는 않는다.

*아래는 원본에 근거한 작성 예시이며, 실제 생성 결과는 아니다.*

| 구분 | Wiki에 담을 내용 | 원본 근거 |
| --- | --- | --- |
| 현재 규칙 (`v30.md`) | 목요일 오후·공휴일 전날·12/22~1/2에는 배포하지 않는다. | 가이드 v30의 현재 규칙 |
| 변경 이력 (`v22.md`) | v22에서 금요일 오후 금지를 목요일 오후 금지로 변경했다. | 가이드 v22의 변경 항목 |
| 변경 이유 (`v22.md`) | 주간 정산 배치 중 배포가 실행돼 정산이 실패했다. 상세 사건은 `incidents/18.md`로 연결한다. | 장애 #18의 원인·조치 |

출처와 시점은 다음 기준으로 관리한다.

- **현재의 기준:** Wiki 구축에 사용한 원본 시점.
- **출처:** 주장·절마다 원본 문서 ID와 위치 연결. 관련 Wiki 링크와 구분.
- **상충 내용:** 판단할 근거가 부족하면 확인 필요로 표시. 인과관계도 근거가 있을 때만 작성.

## 구현 3 — Wiki를 읽으며 질문을 이어간다

**질문 → 전체·주제 목차 → 필요한 Wiki 페이지·관련 링크 → 출처를 붙인 답변**

작은 Wiki에서 목차와 링크 탐색부터 검증한다. **기존 원본 검색의 `vector`·`hybrid`·`keyword`와 해당 검색을 사용하는 답변 기능은 유지하고, Wiki 기반 질의를 별도 경로로 추가한다.** Wiki 임베딩이나 별도 벡터 DB는 추가하지 않는다.

| 단계 | 처리할 내용 |
| --- | --- |
| 탐색 | 전체 목차에서 주제를, 주제 목차에서 필요한 페이지를 선택. 선택한 본문의 관련 링크는 1단계까지 탐색하고 본문은 최대 3개 페이지로 제한 |
| 답변 | 읽은 Wiki로 답하고 핵심 내용 뒤에 `[1]`, `[2]` 표시. 근거 부족 시 명시 |
| 출처 | 번호별 Wiki 페이지·절과 원본 문서·위치 반환 |
| 후속 질문 | 최근 대화와 이전 Wiki 정보로 질문의 대상을 해석한 뒤, Wiki에서 근거 재확인 |

목차 읽기와 본문 읽기 모두 입력 토큰 예산에 포함한다. 선택한 페이지·절, 탐색 경로, 읽은 목차·본문의 토큰 수를 기록해 파일 분할이 실제 읽기 범위를 줄이는지 확인한다. 기존 API·MCP에 연결하고, 대화 이력은 요청으로 전달하는 방식부터 시작한다.

## 구현 후 비교 — 기존 검색과 Wiki 기반 답변

LLM Wiki 구현 후 **`vector`·`hybrid`·`keyword`와 Wiki 기반 질의**를 같은 원본·질문으로 비교한다. 답변 내용·누락·현재/과거 구분·출처·응답 시간·토큰 사용량을 기록하고, 개선·동일·퇴보를 모두 확인한다. 시간은 반복 측정하며 Wiki 생성 비용은 별도로 기록한다.

[v2](https://github.com/hhk22/llm-wiki/blob/30b5274/blogs/02-search-quality.md)는 저장 후보와 DB를 이용한 검색 재평가에서 문서 Hit@3 **20/20**을 기록했다. 이는 문서 확보 지표이며, 답변 정확도와는 구분한다.

**기존 20문항·정답은 유지한다.** 종합·후속·근거 부족 질문은 구현 전에 별도 세트로 고정하고 점수를 분리한다. 기대 답은 원본에서 확인한다.

v2 문서 Hit@3와 v3 Wiki 페이지 적중률은 대상이 달라 직접 비교하지 않는다. 공통 기준은 **핵심 답변의 정확성과 원본 근거**다. 출처 목록에 문서가 있는 것만으로 성공 처리하지 않고, 읽은 Wiki 절과 원본이 답변을 뒷받침하는지 확인한다.

| 검증 대상 | 확인할 내용 |
| --- | --- |
| Wiki 생성 | 현재·과거 규칙의 혼합, 원본 내용 누락, 근거 없는 종합 |
| 링크와 출처 | 존재하지 않는 페이지·절·문서 참조, 주장과 출처의 불일치 |
| 기존 20문항 | 핵심 답변과 원본 근거 유지, 기존 성공 질문의 퇴보 |
| 종합·후속 질문 | 필요한 여러 근거 확보, 생략된 대상 해석, 현재와 과거 구분 |
| 근거 부족 질문 | 원본에 없는 내용을 만들어 답하지 않는지 |
| 시간과 비용 | Wiki 구축 비용과 질문별 응답 시간·모델 호출·입출력 토큰 |

### 후속 질문은 세 조건으로 비교한다

| 조건 | 확인할 효과 |
| --- | --- |
| A. v2 그대로 | 현재 구현의 기준선 |
| B. v2 + 대화 맥락 처리 | A 대비 대화 맥락의 효과 |
| C. v3 + 같은 대화 맥락 처리 | B 대비 Wiki의 효과 |

B·C는 같은 대화 이력·질문 해석 방식·답변 모델·입력 토큰 한도를 사용한다. Wiki 생성·페이지 선택의 모델과 프롬프트, 탐색 한도도 고정해 기록한다. 원본 검색을 추가하는 실험은 Wiki만 읽는 결과와 분리한다.

A·B는 `vector`·`hybrid`·`keyword`별로 결과를 나누어 기록한다.

**v3 답변 품질은 미측정이다.** 질의 기능 구현 후 생성된 Wiki·탐색 기록·전후 답변을 근거로 성공과 실패를 기록한다.

## 다음 단계 — 원본 변경에 따른 Wiki 갱신

v3는 고정된 원본으로 Wiki를 구축하고 질의 효과를 검증한다. 원본을 수정하면 수동으로 전체를 다시 생성한다.

원본 하나의 변경이 어떤 Wiki에 영향을 주는지 추적하고, 필요한 부분만 갱신하는 기능은 **v4의 변경 감지·부분 갱신·이력 관리**로 이어간다.
