# LLM Wiki v3 — 원본 문서를 종합해 Wiki로 만들기

> **원본 120개 → 내용·출처·관계를 정리한 Wiki → 목차를 따라 읽고 답변**

*Wiki 생성과 현재·과거 구분, 변경 이력·상충 검토까지 구현했다. Wiki 기반 질의·후속 질문과 기존 검색 대비 평가는 다음 단계다.*

## 왜 LLM Wiki로 전환하려는가?

### v2의 문제점

> “배포 금지 시간이 금요일 오후에서 목요일 오후로 바뀐 이유가 뭐야?”

v2는 이 질문에 답하기 위해 **가이드 검색 → ‘이유’ 항목의 장애 참조 확인 → 장애 문서 조회 → 답변 생성**을 수행한다. 가이드 v22에서 변경 내용을 찾고, 장애 #18에서 주간 정산 배치와 배포가 겹쳐 정산이 실패한 사건을 읽는다.

답변을 만들 수는 있지만, **두 문서를 종합한 설명은 저장되지 않는다.** 비슷한 질문이 들어오면 다시 검색하고 내용을 연결해야 한다.

### LLM Wiki 전환으로 기대하는 점

**규칙·변경 이유·출처를 Wiki에 미리 정리하고, 여러 질문에서 재사용한다.**

| 기대 효과 | Wiki에서 바꾸는 점 |
| --- | --- |
| 반복되는 종합 부담 감소 | 가이드의 변경 내용과 원인 장애를 함께 설명해 저장 |
| 현재·과거 혼동 감소 | 최신 규칙과 버전별 이력을 구분하고 서로 연결 |
| 필요한 근거의 누락 감소 | 목차·관련 링크로 이유와 이전 규칙을 찾아갈 경로 제공 |

답변 품질과 시간·비용이 실제로 개선되는지는 질의 기능 구현 후 측정한다. 후속 질문의 대상을 이해하는 대화 맥락 처리도 별도로 필요하다.

## 구현 1 — 원본을 읽고 Wiki를 생성한다

`sources/`의 가상 문서 120개를 보존하고, **LLM이 종합한 내용을 `wiki/`에 저장**한다. 배포 버전·장애 사건·오류 코드·FAQ별로 페이지를 나눠 목차에서 필요한 문서를 고를 수 있게 했다.

| 경로 | 역할 |
| --- | --- |
| `wiki/index.md` | 배포·장애·오류·FAQ 주제로 이동하는 전체 목차 |
| `wiki/<주제>/index.md` | 주제 안의 페이지 안내. 배포 목차에는 최신 버전 표시 |
| `wiki/deployments/v22.md` | v22 당시 규칙, 변경 이유, 관련 장애와 출처 |
| `wiki/incidents/18.md` | 장애 #18의 원인·조치와 관련 정책 |
| `wiki/errors/E-009.md` | 오류 코드의 증상·원인·대응 |
| `wiki/onboarding/Q02.md` | FAQ 답변과 상세 규칙으로 이동하는 링크 |

### 생성은 어떤 순서로 진행되는가?

[`WikiBuilder.build()`](../src/llm_wiki/wiki_build.py)는 다음 순서로 동작한다.

| 순서 | 처리 | 결과 |
| --- | --- | --- |
| 1. 원본 선택 | 코드가 대상 문서와 명시적 참조로 연결된 원본을 모음 | LLM이 함께 읽을 본문·ID·메타데이터 |
| 2. 내용 작성 | LLM이 원본을 종합하고, 코드는 응답 형식·인용·필수 근거를 검증 | 페이지별 요약·본문·원본 인용 |
| 3. 관계 연결 | 전체 페이지의 요약·출처 목록을 보고 LLM이 관련 페이지 선택 | 관련 Wiki ID와 연결 이유 |
| 4. 목차 생성 | LLM이 주제별 페이지를 묶고, 주제 안내를 모아 전체 목차 작성 | 주제 목차 4개와 전체 목차 1개 |
| 5. 시점·이력 보강 | 코드가 배포 규칙의 변화를 계산하고 LLM이 상충 후보 검토 | 적용 시점·변경 이력·확인 필요 항목 |
| 6. Markdown 저장 | 코드가 정해진 형식으로 렌더링하고 실제 경로·출처 행 번호 부착 | 본문 120개와 목차 5개 |

예를 들어 [배포 v22 Wiki](../wiki/deployments/v22.md)는 **가이드 v22의 금요일→목요일 변경과 장애 #18의 정산 실패를 함께 설명**하고, 원본 행 번호와 장애 Wiki 링크를 붙인다.

LLM에는 구조화된 응답 형식을 지정한다. 인용이 원문과 다르거나 필수 근거가 빠지면 오류를 전달해 재시도한다. 완료된 작업은 저장해 재개 시 다시 검증하고 재사용한다.

생성 입력에는 평가 질문·정답을 넣지 않는다. 원본·코드 해시, 모델, 프롬프트, 응답, 토큰 사용량은 `wiki/_build/`에 보관한다.

## 구현 2 — 현재 규칙·변경 이력·상충 후보를 구분한다

초기 생성에서는 과거 페이지에도 `현재 규칙`이라는 제목이 남았고, 최신 v30에서 규칙별 변경 버전으로 바로 이동하기 어려웠다. 이를 **시점 표시와 이력 렌더링 규칙**으로 보강했다.

### 현재와 과거를 어떻게 연결하는가?

같은 배포 가이드 계열에서 가장 큰 버전을 최신으로 삼는다. 현재 원본에서는 v30이며, 과거 페이지는 `v22 당시 규칙`처럼 표시하고 최신 가이드 링크를 붙인다.

변경 이력은 코드가 **연속 버전의 `현재 규칙` 절에서 같은 이름의 항목을 비교**해 만든다. 공백 서식 차이는 제외하고, 변경 전후 값과 출처를 남긴다. 원인 장애는 해당 버전의 ‘이유’ 항목에 명시된 경우에 연결한다.

| 실제 생성 결과 | 읽을 수 있는 내용 |
| --- | --- |
| [v30](../wiki/deployments/v30.md)의 현재 규칙 | 목요일 오후·공휴일 전날·12/22~1/2 배포 금지 |
| v30 → [v22](../wiki/deployments/v22.md) | 금요일 오후에서 목요일 오후로 바뀐 전후 값과 이유 |
| v30 → [장애 #18](../wiki/incidents/18.md) | 변경 이유에 명시된 정산 배치·배포 충돌 사건 |
| v30 → [v25](../wiki/deployments/v25.md) | 12/22~1/2 연말 동결이 추가된 이력 |
| 과거 v22 페이지 | v22까지의 이력과 최신 가이드 링크. 이후 v25 변경은 제외 |

이 방식으로 **규칙 항목 변경 14건**을 연결했다. 빠진 버전이나 필드의 변경 시점은 추측하지 않는다. 현재의 기준은 Wiki 구축에 사용한 원본이며, 모든 자유 형식 문장의 변화를 추적하는 기능은 아니다.

### 문서끼리 다른 말을 하면 어떻게 하는가?

배포 관련 원본의 본문·메타데이터와 코드가 계산한 이력을 LLM에 전달한다. 버전 차이로 설명되지 않는 모순은 **양쪽 원문과 함께 `확인 필요`로 표시**하고, 어느 쪽이 맞는지 자동 결정하지 않는다.

| 검토 조건 | 결과 |
| --- | --- |
| 실제 배포 관련 원본 67개 | 상충 후보 0건 |
| 별도 실험: 정상 버전 이력과 FAQ | 후보 0건 |
| 별도 실험: FAQ를 “현재 목요일 오후 배포 허용”으로 변경 | FAQ와 v30 사이 후보 1건 |

별도 실험은 원본 파일을 수정하지 않고 입력만 바꿔 각 1회 실행했다. **후보 0건이 상충 부재를 증명하거나, 이 실험이 전수 탐지 성능을 보장하지는 않는다.**

## 검증 결과 — Wiki 구축까지 완료했다

생성 모델은 `gemini-3.5-flash-lite`다. 기존 생성 작업 33개를 재검증해 재사용하고, 시점·이력·상충 검토를 반영해 Markdown을 다시 저장했다.

| 확인 항목 | 최신 결과 |
| --- | --- |
| 생성 파일 | 본문 120개·목차 5개, 누락·중복 없음 |
| 링크 | 2,166개 대상 확인 |
| 생성 본문의 근거 인용 | 978개 원문 일치 |
| 시점·이력 | 원본에서 다시 계산·렌더링해 저장된 페이지와 대조 |
| 코드 검증 | DB 연동 포함 테스트 146개 통과, Ruff 통과 |

인용 일치와 링크 검증만으로 설명의 의미·인과관계·완전성까지 보장하지는 않는다. **Wiki를 이용한 답변 품질은 아직 미측정이다.** 호출·토큰·검증 범위는 [초기 생성 기록](../evaluation/wiki-build-review.md)과 [이력·상충 검증 기록](../evaluation/wiki-history-review.md)에 남겼다.

## 남은 구현 — Wiki를 읽고 질문에 답한다

**질문 → 전체·주제 목차 → 필요한 페이지·관련 링크 → 원본 출처를 붙인 답변**

기존 **`vector`·`hybrid`·`keyword` 검색과 검색 기반 답변을 모두 유지**하고, Wiki 질의를 별도 경로로 API·MCP에 추가할 예정이다. Wiki 임베딩이나 별도 벡터 DB는 추가하지 않는다.

| 구현할 기능 | 동작과 제한 |
| --- | --- |
| Wiki 탐색 | 목차에서 페이지 선택. 관련 링크 1단계, 본문 최대 3개 페이지. 목차와 본문 모두 입력 토큰 한도에 포함 |
| 근거 기반 답변 | 읽은 내용으로 답하고 `[1]`, `[2]`에 Wiki 절·원본 문서·위치를 연결. 근거 부족 시 명시 |
| 후속 질문 | 요청으로 받은 대화 이력에서 대상을 해석하고, Wiki에서 근거 재확인 |
| 관찰 기록 | 선택한 페이지·절·탐색 경로, 응답 시간·모델 호출·입출력 토큰 기록 |

예를 들어 “현재 배포 금지 시간과 그 이유”에 답한 뒤, **“그럼 바뀌기 전에는?”의 대상이 배포 금지 시간임을 해석하고 이전 규칙을 찾아 답하는 흐름**을 구현한다.

## 질의 구현 후 — 기존 검색과 같은 조건으로 비교한다

기존 20문항·정답은 유지하고, 종합·후속·근거 부족 질문은 질의 구현 전에 별도 세트로 고정한다. 같은 원본·질문으로 **답변 내용과 누락, 현재·과거 구분, 원본 출처, 시간·토큰**을 비교한다.

[v2의 문서 Hit@3 20/20](https://github.com/hhk22/llm-wiki/blob/30b5274/blogs/02-search-quality.md)은 필요한 문서를 확보한 결과다. Wiki 페이지 적중률과 직접 비교하지 않고, **답변이 정확하며 읽은 근거와 원본이 이를 뒷받침하는지**를 공통 기준으로 삼는다.

후속 질문에서는 대화 맥락 처리의 효과와 Wiki의 효과를 구분한다.

| 비교 조건 | 확인할 효과 |
| --- | --- |
| A. 기존 검색·답변 그대로 | 기준선 |
| B. 기존 검색·답변 + 대화 맥락 처리 | A 대비 맥락 처리의 효과 |
| C. Wiki 답변 + 같은 대화 맥락 처리 | B 대비 Wiki의 효과 |

A·B는 `vector`·`hybrid`·`keyword`별로 기록한다. B·C의 대화 이력·질문 해석 방식·답변 모델·입력 토큰 한도를 맞추고, Wiki 생성·페이지 선택 설정도 고정해 남긴다. 원본 검색까지 추가하는 실험은 Wiki만 읽은 결과와 분리한다.

개선·동일·퇴보를 모두 기록하고 시간은 반복 측정한다. Wiki 사전 생성 비용도 별도로 포함해 전환의 효과를 판단한다.

## v4로 이어질 작업 — 원본 변경에 따른 Wiki 갱신

v3는 고정된 원본의 Wiki 구축과 질의 비교까지 진행한다. 원본이 바뀌면 수동으로 전체를 다시 생성하며, **변경 감지·영향받는 Wiki의 부분 갱신·갱신 이력 관리**는 v4에서 다룬다.
