# LLM Wiki — 프로젝트 설계

> 사내 문서를 쉽게 찾고, 최신 문서를 근거로 질문을 이어갈 수 있는 Wiki를 만든다.

## 시작 배경

업무에 AI Agent를 활용하다 보면 이런 생각이 들 수 있다.

- **필요한 사내 문서도 AI Agent에게 물어서 찾을 수 없을까?**
- **찾은 문서를 대화의 맥락으로 삼아, 추가 질문까지 이어갈 수 없을까?**

문서를 찾는 과정과 그 내용을 이해하고 업무에 적용하는 과정이 하나의 대화로 이어지는 경험을 목표로 한다.

이런 흐름을 지원하는 **LLM Wiki**를 만들어보려 한다. 사내 구현·배포 경험을 바탕으로, 가상 문서를 활용한 공개 프로젝트의 설계와 구현 과정을 기록한다.

## 누가, 어떻게 사용할까?

대상은 **업무 중 사내 문서를 찾아보는 모든 구성원**이다. 출장비 정산을 예로, 다음과 같은 사용 흐름을 구현하려 한다.

## 버전별 전개

RAG 기준선을 만들고 검색 품질을 개선한 뒤, 그래도 해결되지 않는 문제를 근거로 LLM Wiki로 전환한다. 이후 지식 갱신과 운영 문제를 해결하며 서비스로 발전시키는 과정을 버전별로 기록한다.

| 버전 | 구현할 내용 |
| --- | --- |
| **v1 · RAG 기준선** | 가상 사내 문서 약 120개를 청킹·임베딩하고, 벡터 검색과 출처 기반 답변을 구현한다. 키워드 검색과 함께 평가 세트로 유형별 Hit@K를 측정한다. |
| **v2 · 검색 품질 개선** | 키워드 + 벡터 hybrid, 문서 유형·최신 버전 필터, reranker를 적용해 같은 평가 세트로 재측정한다. 개선되는 유형과 그대로인 유형을 구분한다. |
| **v3 · LLM Wiki 전환** | 검색 개선으로 해결되지 않는 문서 간 종합·후속 질문·버전 충돌을 근거로, LLM이 주제별 Wiki·목차·관련 링크·출처를 생성하는 구조로 전환한다. |
| **v4 · 지식 갱신** | 원본 문서 변경을 추적해 관련 Wiki를 갱신하고, 버전·변경 이력·상충 내용을 관리한다. |
| **v5 · 성능과 안정성** | 처리 병목과 동시성 오류를 재현하고, Worker·작업 상태·멱등성·재시도로 해결한다. |
| **v6 · 운영 피드백** | 질의 성공·실패, 응답 시간과 사용자 피드백을 관찰하고, 병목이 확인되면 Redis 캐시와 cache hit/miss를 측정한다. |
| **v7 · 서비스 완성** | 접근 제어, 운영 화면, Docker Compose 실행 환경, 자동 테스트와 배포·데모를 완성한다. |
